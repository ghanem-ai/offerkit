## Local: Docker compose

The provided `docker-compose.yml` boots four services. `web` and `worker` use the same published image, `ghcr.io/offerkit/offerkit`:

- `web` — Next.js dashboard + REST API on `:3000`
- `worker` — long-running Node process pulling jobs out of the queue
- `postgres` — Postgres 17 on `:5432`
- `redis` — Redis 7 on `:6379`

```bash
cp .env.example .env
# Required:
#   DATABASE_URL=postgres://offerkit:dev@postgres:5432/offerkit
#   BETTER_AUTH_SECRET=…
#   WEBHOOK_SECRET_ENCRYPTION_KEY=… # openssl rand -base64 32
#   ADMIN_EMAIL=…
#   ADMIN_PASSWORD=…
#   OFFERKIT_PUBLIC_URL=http://localhost:3000
docker compose up -d
```

`web` runs migrations before starting Next.js, so a fresh DB is fully migrated on first boot. The `worker` reclaims orphaned jobs on startup and re-seeds the recurring `loyalty.points.expire` and `events.prune` sweeps if they're missing.

Pin a release by setting `OFFERKIT_IMAGE_TAG`, for example:

```bash
OFFERKIT_IMAGE_TAG=v0.1.0 docker compose up -d
```

The runtime image is distroless: it runs as a non-root user, ships no shell or package manager, and its entrypoint is already `node`, so a service command is just a script path (`apps/worker/dist/index.js`).

Image channels are intentionally narrow: `edge` follows the latest `main` commit, `latest` follows the newest stable version, and stable versions are published as both `v0.1.0` and `0.1.0`.

Contributors who need to test local source changes can build the same image shape:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```

## Production: Railway

Railway should deploy the published image directly. Do not connect the monorepo as a GitHub source.

In one Railway project, create:

- Postgres
- Redis
- `web` Docker Image service using `ghcr.io/offerkit/offerkit:latest`
- `worker` Docker Image service using `ghcr.io/offerkit/offerkit:latest`

For production, pin both image services to a version tag such as `ghcr.io/offerkit/offerkit:v0.1.0` instead of `latest`.

Set these variables on `web`:

```
DATABASE_URL=postgres://...
REDIS_URL=redis://...
ADMIN_EMAIL=…
ADMIN_PASSWORD=…
BETTER_AUTH_SECRET=…
WEBHOOK_SECRET_ENCRYPTION_KEY=…
OFFERKIT_PUBLIC_URL=https://your-domain
```

`web` uses the image default command and should expose a public domain. Configure its healthcheck path as `/api/v1/ready`.

`/api/v1/ready` reports `checks.db` from a live query. Set `WORKER_READINESS_URL` to report `checks.worker` by calling the worker's own `/ready` endpoint; when it is unset the worker check is `null` and no deployment-specific hostname is guessed. The worker check is informational and does not change the reported `status`.

Set these variables on `worker`:

```
DATABASE_URL=postgres://...
REDIS_URL=redis://...
WEBHOOK_SECRET_ENCRYPTION_KEY=…
```

Override the `worker` start command. The image entrypoint is already `node`,
so the command is just the script path:

```bash
apps/worker/dist/index.js
```

`worker` should not expose a public domain. Configure its healthcheck path as `/health`.

## Production: Diploi

Diploi should use the same deployment shape as Docker compose and Railway:

- `web` — public HTTP component from `ghcr.io/offerkit/offerkit`, exposes `:3000`
- `worker` — private/background component from `ghcr.io/offerkit/offerkit`, command `apps/worker/dist/index.js`, exposes health on `:9091`
- `postgres` — managed Postgres service wired into both components as `DATABASE_URL`
- `redis` — Redis service wired into both components as `REDIS_URL`; BullMQ stores background jobs here

Required `web` environment variables:

```
DATABASE_URL=postgres://...
REDIS_URL=redis://...
BETTER_AUTH_SECRET=…
WEBHOOK_SECRET_ENCRYPTION_KEY=…
OFFERKIT_PUBLIC_URL=https://your-diploi-domain
ADMIN_EMAIL=…
ADMIN_PASSWORD=…
```

Required `worker` environment variables:

```
DATABASE_URL=postgres://...
REDIS_URL=redis://...
WEBHOOK_SECRET_ENCRYPTION_KEY=…
WORKER_HEALTH_PORT=9091
```

Use the README's **Launch with Diploi** button if you want to start from Diploi's project wizard. After the first deploy, verify `/api/v1/ready` on `web`, `:9091/health` on `worker`, and sign in with the seeded admin account.

## Single sign-on (SAML)

Public sign-up is disabled: accounts are seeded from `ADMIN_EMAIL` / `ADMIN_PASSWORD`, created by an admin under **Settings → Users**, or provisioned on first SSO login. Disabled accounts (`disabledAt` set) cannot start a session by any path.

Set `SAML_ENABLED=true` on `web` to make `/sign-in` lead with a **Continue with Ghanem SSO** button, with the email/password form kept as **Emergency access**. `SAML_IDP_CERTIFICATE` is required when SSO is enabled — the auth layer throws on first use without it.

```
SAML_ENABLED=true
SAML_PROVIDER_ID=authentik                 # also the last path segment of the ACS URL
SAML_IDP_SSO_URL=https://your-idp/application/saml/offerkit/sso/binding/redirect/
SAML_IDP_ENTITY_ID=https://your-idp/application/saml/offerkit/metadata/
SAML_IDP_CERTIFICATE=…                     # IdP signing certificate (PEM body)
SAML_SP_ENTITY_ID=…                        # defaults to OFFERKIT_PUBLIC_URL
SAML_EMAIL_DOMAIN=ghanem.sa
SAML_GROUPS_ATTRIBUTE=http://schemas.xmlsoap.org/claims/Group
SAML_ADMIN_GROUP=platform-admins
SAML_ALLOW_IDP_INITIATED=false
```

Register OfferKit with the IdP using:

- **ACS / reply URL** — `<OFFERKIT_PUBLIC_URL>/api/auth/sso/saml2/sp/acs/<SAML_PROVIDER_ID>`
- **Entity ID / audience** — `SAML_SP_ENTITY_ID` (or `OFFERKIT_PUBLIC_URL`)
- **SP metadata** — `<OFFERKIT_PUBLIC_URL>/api/auth/sso/saml2/sp/metadata?providerId=<SAML_PROVIDER_ID>`
- **NameID format** — email address

`SAML_EMAIL_DOMAIN` does not restrict which addresses may sign in — the sign-in button starts the flow by `SAML_PROVIDER_ID`, and the group claim decides the role — it is used for email-domain-based provider lookup.

Assertions must be signed (SHA-256 digests and signatures), carry timestamps, and arrive within a 5-minute clock skew. Every login re-reads the group claim named by `SAML_GROUPS_ATTRIBUTE`: members of `SAML_ADMIN_GROUP` get the `admin` role and a present claim without that group maps to `member`, so revoking group membership in the IdP downgrades the account on the next sign-in. If the configured claim is absent, OfferKit preserves the existing role and logs a warning instead of silently demoting the account. `SAML_ALLOW_IDP_INITIATED=true` accepts unsolicited IdP-initiated responses, which skips `InResponseTo` replay validation — leave it off unless your IdP requires it.

## Retention and rate limits

API keys with a `rateLimitRps` limit are throttled through a shared Postgres sliding window (`api_rate_limit`), so the limit holds across every `web` replica. Expired window rows are swept opportunistically; no maintenance job is needed.

Failed validations are recorded as `voucher.validation_failed` events to power the insights failure breakdown. They fan out only to webhooks explicitly subscribed to that event, not broad `*` subscriptions. The recurring `events.prune` job deletes them in bounded batches after `EVENT_RETENTION_DAYS` (default 30). Other event types are never pruned.

## Observability

The image is OpenTelemetry-ready out of the box. Set:

```
OTEL_EXPORTER_OTLP_ENDPOINT=https://api.axiom.co
OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer <AXIOM_TOKEN>,X-Axiom-Dataset=offerkit
```

…and you'll get traces and metrics from `apps/web` and `apps/worker` in the same dataset, separable by `service.name`. Set `OTEL_SDK_DISABLED=true` to opt out entirely.

## Multi-environment

The model is "run two deploys" — each environment is its own Railway project with its own Postgres. There's no concept of a logical environment within a single deployment. Staging and production roll forward independently.
